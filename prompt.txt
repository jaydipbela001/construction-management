# Build a Complete Construction Management Admin Panel

## 1. Project Overview

Build a complete, production-oriented Construction Management Admin Panel for managing multiple independent construction projects.

This is a simple construction management application for a single administrator. There is no customer panel, contractor panel, employee panel, or public registration system.

The admin should be able to create multiple construction projects and manage custom construction materials, prices, quantities, and expenses separately for each project.

The application must be fully functional, responsive, maintainable, and deployable on Vercel.

Do not build only a UI prototype. Implement the frontend, backend APIs, MongoDB integration, authentication, CRUD operations, validation, loading states, and error handling.

### Project Details

* Display all project information.
* Show project-specific materials.

### Critical business rule

Creating a new construction project must not automatically create any material entries.

Every new project must begin with an empty materials list and an empty expense list unless data is explicitly added by the admin.

Never copy materials, expenses, or other records from an existing project when creating a new project.

Each project must remain independent of all other projects.

When a project is selected, all project-specific operations must use its MongoDB project ID.

Deleting a project must never accidentally delete records belonging to another project.

For destructive operations, show a confirmation dialog. Use a documented and safe policy for related materials and expenses, such as a MongoDB transaction where supported or an explicit archive/restriction strategy.

## 8. Project-Specific Materials Module

This is one of the most important modules.

Each construction project has its own materials list.

There must be no predefined materials automatically inserted into a project.

The admin creates every material manually.

Examples of materials the admin might create:

* Iron or steel.
* Wood.
* Sand.
* Cement.
* Bricks.
* Gravel.
* Tiles.
* Paint.
* Pipes.
* Electrical materials.
* Any custom construction material.

These are examples only, not default database records.

### Add Material Form

Fields:

* Material name — required.
* Category — optional.
* Description — optional.
* Quantity — required and greater than zero.
* Unit — required, such as kg, ton, bag, piece, cubic meter, liter, or another custom unit.
* Unit price — required and non-negative.
* Supplier — optional.
* Purchase date — optional.
* Notes — optional.

The admin should be able to enter a custom material name and a custom unit.

Do not restrict material creation to a fixed predefined dropdown of material names.

If a unit selector is provided, include a Custom option that allows the admin to enter another unit.

### Material List

For the selected project, display:

* Material name.
* Category.
* Quantity.
* Unit.
* Unit price.
* Total estimated material value.
* Supplier.
* Actions.

Calculate:

lineTotal = quantity × unitPrice

Calculate the estimated material value for a project by summing its material line totals.

Format currency consistently and use a configurable currency setting, initially INR (₹).

Do not hardcode currency formatting independently in every component.

### Material Operations

Implement:

* Create material.
* Read materials for the selected project.
* Edit material.
* Delete material with confirmation.
* Search materials.
* Filter by category.
* Sort and paginate where appropriate.

When editing quantity or price, update the displayed line total immediately using validated values and persist the changes through the backend.

### Project Isolation

A material must belong to exactly one construction project.

Store projectId as a MongoDB ObjectId reference.

Every material API must validate the requested project and enforce project ownership within the current admin's authorized data scope.

For example, a material created in Project A must not appear in Project B.

The same material name may be used in both projects with different quantities, units, and prices.

Do not create a global inventory catalog as a mandatory feature. This application's primary requirement is independent, project-specific material management.

## 12. Required Vercel Serverless Architecture

The entire application must be designed for Vercel deployment.

IMPORTANT: Vercel serverless functions are not ordinary, continuously running Express servers. Do not rely on app.listen() as the production startup mechanism.

Use the following architecture:

* The React frontend is built with Vite.
* The backend is exposed through a Vercel-compatible serverless function.
* Express is exported as a request handler.
* MongoDB connections are reused and cached across warm function invocations where possible.
* Every function invocation must be able to initialize safely when required.
* No API should depend on in-memory state persisting between requests.
* Do not use local files as a persistent database.
* Do not depend on background processes, permanent in-process schedulers, or long-running server connections.
* Keep API handlers compatible with Vercel's request and response lifecycle.
* Avoid starting a separate production Express listener.
* Ensure all API endpoints are routed correctly under /api.
* Keep the application compatible with the selected Vercel Node.js runtime.

Use a clear backend entry point such as:

backend/api/index.js

It should export the configured Express application as the serverless request handler.

Create the Express application separately in:

backend/src/app.js

Implement MongoDB connection reuse in:

backend/src/config/db.js

The database connection helper should cache an existing connection or connection promise when possible and avoid opening unnecessary new connections during repeated warm invocations.

Do not assume a single persistent process or global state shared across all serverless instances.

### Vercel routing

Create and document the correct root vercel.json for the chosen monorepo layout.

Ensure the configuration:

* Builds the Vite frontend.
* Exposes backend serverless functions.
* Routes /api requests to the backend.
* Routes frontend page navigation to the React application without overriding API routes.
* Uses valid, supported Vercel configuration syntax.
* Does not depend on an obsolete deployment configuration.

Choose a consistent root-directory and build-output strategy. Do not mix incompatible root-level and subdirectory deployment approaches.

If the selected deployment architecture needs separate Vercel projects rather than one combined project, explain why and provide working configurations for both. Prefer one Vercel project when practical.

Ensure all production API calls use a configurable API base URL. When the frontend and backend are deployed on the same origin, use a relative /api base URL.

For local development, configure Vite to proxy /api requests to the Express development server, or document a supported alternative.

Keep any app.listen() usage limited to local development if it is needed. It must not be required for the production Vercel serverless deployment.

Do not claim deployment compatibility without validating the configuration and explaining the required Vercel project settings.

5. Important Vercel deployment note

For this project, do not simply deploy a traditional Express server and expect it to run continuously on Vercel.

A suitable architecture is:

React + Vite frontend

Build and serve the admin interface

Vercel serverless API

Express routes, controllers, and middleware

/api/projects · /api/materials · /api/expenses

MongoDB Atlas

Persistent projects, materials, expenses, and admin data

The key implementation details are:

Export the Express application as a Vercel-compatible handler rather than depending on app.listen() in production.

Cache MongoDB connections where possible to avoid unnecessary reconnections.

Store credentials and secrets in Vercel environment variables.

Configure routing so /api/* reaches the backend and React routes reach the frontend.

Keep all business data in MongoDB, not in serverless memory or local files.

My recommendation: Build the first version with only four main modules — Dashboard, Projects, Materials, and Expenses — plus admin login. This keeps the application simple while giving you a solid foundation to add purchase tracking, suppliers, reports, or PDF exports later.
